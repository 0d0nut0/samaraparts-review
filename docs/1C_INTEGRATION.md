# Обмен с 1С:УТ 11 — состояние и контракт от 04.11.2026

Источник номенклатуры, закупки и партий — 1С. Сайт сопоставляет товары с Moba и рассчитывает продажные цены.

## Проверенное состояние облачной базы

Полный цикл работает через стандартный REST/OData, опубликованный после явного
подтверждения владельца. На сайт привязаны 7 033 товара по GUID, получена закупка
324 товаров из одного проведённого поступления. Склад при обмене не меняется.
В 1С созданы виды цен «Розница», «ОПТ», «СуперОПТ» и проведены четыре документа
установки цен № 00-00000001–00-00000004: 3 432 строки для 1 554 товаров.
Все записанные значения прочитаны обратно из регистров и сверены. Повторный
запуск: 0 изменённых цен, 0 новых документов.

Публикация содержит 408 автоматически связанных типов данных и регистр штрихкодов.
Среди зависимостей есть банковские счета, контрагенты и физические лица; этот состав
был раскрыт владельцу перед разрешением публикации. Наличие типа в метаданных
не доказывает отсутствие или наличие доступа к каждой его записи.
Код обмена читает товары, штрихкоды, валюту, закупочные документы и цены; записывает
только виды цен и документы установки цен. Закупки и банковские документы не изменяет.

Лимит сеансов преодолён после согласования с владельцем. Для `api_user`
создан профиль `PARTS - catalog and prices` и группа `PARTS - integration`.
Пользователь исключён из групп «Администраторы» и «Открытие внешних отчетов и обработок»;
права остальных пользователей этих групп сохранены. В карточке API-пользователя
проверены 7 разрешённых ролей: базовые БСП/УТ, OData, чтение номенклатуры,
чтение приобретений товаров/возвратов поставщикам, чтение и изменение цен.
Клиентский вход не разрешён ролями, что для служебного пользователя ожидаемо.
Чтение товаров/закупок и запись цен реально проверены от `api_user`.
Пароль администратора не используется службой обмена.

## Что реализовано на сайте

- `/1c_exchange`: CommerceML `checkauth → init → file → import`. Авторизация отдельной парой логин/пароль из `.env`; файлы изолированы по сессиям, XML разбирается с защитой от XXE, объём ограничен.
- Товары сопоставляются по GUID 1С, артикулу, штрихкоду. Для первоначально загруженного вручную каталога есть проверенная карта 7 033 наименований 1С → SKU (`var/onec_catalog_map.json`). Неоднозначные совпадения автоматически не объединяются. Характеристики с `#` пропускаются, пока для них нет отдельного учёта.
- Полное название сайта сохраняется, если 1С присылает только первые 100 символов.
- Из `offers.xml` принимается только явно названный вид закупочной цены `ONEC_PRICE_TYPE_PURCHASE` (сейчас `Закупочная`). Первый случайный вид цены не принимается за розницу.
- После импорта выполняется сопоставление с полным снимком Moba не старше 24 часов. Без снимка новые товары остаются без продажной цены до следующего парсинга.
- Парсер `python run_parser.py --apply` обновляет существующий каталог сайта. Новые чужие товары Moba автоматически не добавляет, остатки не меняет. Неполный снимок не применяется. Снимок, отчёт и копия прежних цен сохраняются в `var/prices`.
- `GET /1c/prices` (HTTP Basic, те же учётные данные обмена) отдаёт JSON с GUID/SKU, тремя ценами и временем парсинга. Закупки и персональные данные покупателей в этот ответ не входят.
- В админке «Интеграция с 1С» доступен CSV рассчитанных цен.

## Правила

ОПТ = обычная розничная Moba. Розница = ОПТ × 1,20. СуперОПТ = max(ОПТ × 0,90; закупка × 1,15).
Цены продажи — в целых рублях, граница закупка × 1,15 округляется вверх. Без известной закупки суперопт не публикуется; такому аккаунту доступен ОПТ. Тариф назначает администратор, доставка не добавляет скидку.

Цена из предыдущего снимка сохраняется при исчезновении товара из свежего снимка с пометкой `stale_moba` в отчёте; время парсинга не обновляется. Такие позиции требуют проверки менеджером.

## Автоматический цикл и работа сотрудников

1. Создайте товар в номенклатуре 1С. Укажите название и штрихкод, избегая дублей.
2. Закупочную стоимость укажите в проведённом документе приобретения товаров.
   Служба берёт последнее проведённое поступление в рублях: фактическая сумма строки
   с НДС / количество в базовых единицах. НДС в текущем поступлении отсутствует.
   Это цена последней закупки для наценки, а не партийная себестоимость FIFO.
   Если в 1С отдельно ведётся вид цен «Закупочная», его более новая цена имеет приоритет.
   Продажная цена не принимается за закупочную.
3. Каждые пять минут `com.samaraparts.onec` запускает `run_onec_sync.py --apply`.
   Товары/закупки поступают на сайт, затем цены рассчитываются по последнему полному
   снимку Moba (не старше 24 часов) и возвращаются в 1С. Сам парсер Moba работает
   в 08:15, 12:15, 16:15, 20:15 по Москве, поэтому изменения поставщика видны после парсинга.
4. В документах продажи 1С выбирайте нужный вид цены: «Розница», «ОПТ», «СуперОПТ».
   На сайте тариф покупателю назначает администратор в разделе «Пользователи».

Обычный запуск `python run_onec_sync.py` только проверяет расчёт с откатом транзакции.
`--apply` сохраняет товары/закупки и пишет только изменённые цены в 1С.
Используются документы с таблицей `Товары2_5`; после проведения каждая цена сверяется
через `ЦеныНоменклатуры25_RecordType/SliceLast`. Неопределённые цены не записываются нулями.
Повторные документы предотвращаются проверкой актуальных цен и собственным детерминированным
маркером комментария. Записи после сетевого тайм-аута вслепую не повторяются.

Настройки: `ONEC_ODATA_URL`, `ONEC_ODATA_LOGIN`, `ONEC_ODATA_PASSWORD` в `.env`.
Журналы — `var/log/com.samaraparts.onec*.log`; исходный снимок, планы и резервные копии —
`var/onec-sync`, файлы с ограниченными правами. Не публикуйте `.env` и эту папку.

Узел `PartsSite` по адресу `/1c_exchange` сохранён как альтернативный канал CommerceML;
его проверка авторизации проходила, но рабочий автоматический цикл сейчас использует OData.
Обмен заказами сайта с документами продаж 1С этим циклом не реализован.

## Остатки

Остатки из 1С устанавливаются абсолютно по сопоставленному складу, не добавляются как новый приход. Регистр транзакций сайта фиксирует разницу. Повторный импорт одинаковых остатков не создаёт дубли движений.

На 04.11.2026 `ONEC_IMPORT_STOCKS=false`: сначала нужно сверить склад 1С с подтверждёнными остатками Самары (2 160 шт.) и Казани (123 шт.) и привязать GUID склада к городу в админке. В другом чате в одном из отчётов 1С было 908 шт.; это требует проверки состава/периода отчёта. Не включать синхронизацию количества вслепую.

## Печатная форма и FIFO

На сайте добавлена печать из сохранённого заказа: админка → заказ → «Печать счёта» / «Печать накладной».
Цены берутся из строк оформленного заказа; новая цена Moba не переписывает старый счёт. Сумма строк сверяется с суммой заказа. Реквизиты — ИП Герасимова, без НДС.

HTML/PDF образец не является установленной внешней печатной формой 1С. Для печати непосредственно из 1С нужен макет её печатной формы или подключённая обработка.

В 1С проверено: метод оценки стоимости товаров — `ФИФО (скользящая оценка)`, УСН «Доходы» 6%, продажа «Без НДС».
Это проверка настройки; фактическое распределение себестоимости проведённых продаж и закрытие периода отдельно не проверялись. На сайте нет учёта партий FIFO; его прибыль — оценка по закупочной цене каталога, при неизвестной закупке для нового заказа показывается «—».

## Проверки

`python -m unittest discover -s tests -q` — формулы, округления, сопоставление, импорт закупки, защита от неверного вида цены, повторная загрузка, печатная сумма.
Полный путь регистрации/почты/корзины/заказа проверяется только на отдельной базе, заканчивающейся `_test`, и пустой Redis DB, кроме DB 0. Настоящие письма и уведомления в этих проверках не отправляются.
